# M8.1 — Real-browser differential execution

M8.1 turns the M8 protocol/harness into a real browser-to-browser compatibility gate.

## Reference pair

The Windows differential job executes the same deterministic local fixtures against:

- a native Openbrowser build using CEF `152.0.6+g708dc14+chromium-152.0.7977.83`;
- Chrome for Testing headless shell `152.0.7977.83` (`win64`, revision `1654411`).

The Chromium reference archive is pinned by exact version and repository SHA-256. CI verifies the archive before extraction and also checks the executable-reported version.

## Observation bridge

The production browser does not gain a DOM-inspection backdoor for this test. Instead, compatibility fixtures load `compatibility-observe.js`, which publishes a bounded test observation to a per-run localhost collector protected by an unguessable token.

The common observations now include:

- canonical final URL;
- document title;
- deterministic DOM marker/text values;
- stable fixture events;
- localStorage contents;
- sessionStorage contents where declared by the scenario;
- normalized document cookies where declared by the scenario.

The harness independently records fixture HTTP requests and performs normalization and field-by-field comparison. Request comparison remains strict; browser-default noise is removed at the fixture level rather than hidden by comparator ignore lists.

## Current deterministic corpus

The PR-sized real-browser corpus contains 10 local, versioned scenarios:

1. basic navigation and DOM observation;
2. local redirect-chain resolution;
3. JavaScript DOM mutation plus localStorage persistence;
4. fragment/hash navigation;
5. History API state replacement;
6. same-origin JSON XHR and DOM projection;
7. external same-origin script loading;
8. JavaScript cookie visibility;
9. localStorage and sessionStorage lifecycle semantics;
10. core DOM creation and mutation APIs.

The expanded corpus has completed with `10 passed, 0 incompatible, 0 runner failures` against the pinned Chromium 152 reference. See [`m8.1-compatibility-corpus.md`](m8.1-compatibility-corpus.md) for the corpus-specific contract.

## Lifecycle requirements

The Openbrowser runner remains stricter than a compatibility-only observation:

- the real native browser must launch successfully;
- the fixture must be observed;
- graceful close must be accepted;
- the process must exit with code `0`;
- persisted session state must report `clean_shutdown: true`.

A browser crash, timeout, missing observation, checksum mismatch or bad shutdown is a runner failure and cannot become a compatibility pass.

## Artifacts

The `Web Compatibility Differential` workflow uploads:

- `real-browser-differential.json` — normalized scenario results and differences;
- `reference-metadata.json` — Openbrowser commit, CEF pin, Chromium reference version and downloaded archive SHA-256.

## Relationship to M8.2

M8.2 adds a separate, pinned upstream Web Platform Tests smoke lane. That lane currently validates standards-test ingestion and the Chromium reference environment; it does not yet run Openbrowser directly through `wptrunner` because Openbrowser does not expose a WebDriver-compatible product adapter.

M8.1 therefore remains the direct Openbrowser execution layer, while M8.2 provides the reproducible standards-test boundary. See [`m8.2-wpt-smoke.md`](m8.2-wpt-smoke.md).

## Deliberate next steps

M8.1 does not claim full WPT execution inside Openbrowser, rendering reftests, a broad live-site corpus or exhaustive Web-platform coverage. The next compatibility increments should expand into high-value areas such as Fetch/CORS/CSP, IndexedDB, workers, service workers, WebSockets and deterministic rendering/reftest observations without weakening the strict lifecycle and differential classifications established here.
